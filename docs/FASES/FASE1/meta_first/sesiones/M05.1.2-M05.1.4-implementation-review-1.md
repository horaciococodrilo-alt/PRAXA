## Hallazgos

| ID | Severidad | Archivo:línea | Problema | Evidencia | Corrección propuesta |
|---|---|---|---|---|---|
| R-01 | media | `src/modules/integrations/contract/primitives.ts:129-139` (`redactUrl`) y `connection.ts:185-188` (`toConnectionDto`) | La redacción conserva `origin + pathname`, y las URL de la Graph API llevan la cuenta en la ruta (`/act_<id>/insights`). Un error de transporte o de la API deja el identificador completo en `last_error_message`, que el DTO expone sin truncar en `last_error.message`. CA-09b exige que en la UI el identificador se muestre truncado, y el DTO existe justamente para eso (CA-06) | Sonda: `redactErrorMessage('GET https://graph.example.test/v1/act_sintetica_000123/insights?fields=spend …')` devuelve la ruta con la cuenta completa, y `redactedErrorMessageSchema` acepta un mensaje que la contiene. La prueba "la serialización del DTO no contiene … la cuenta completa" solo usa un mensaje sin cuenta | Dentro de M05.1.2 a M05.1.4: enmascarar en `redactErrorMessage` los segmentos `act_<…>` (por ejemplo con `maskExternalAccountId`), o quitar la ruta de las URL redactadas, y hacer que `redactedErrorMessageSchema` los rechace. Agregar una prueba de DTO con un `last_error_message` que contenga una URL con la cuenta en la ruta, y aseverar que el JSON del DTO no contiene el identificador completo |
| R-02 | baja | `src/modules/integrations/contract/primitives.ts:123-127` | Solo se redactan `clave=valor` y `"clave": "valor"`. La forma `clave: valor` sin comillas, típica de volcados de encabezados o de logs de clientes HTTP (`access_token: …`), pasa intacta, aunque el comentario de `redactErrorMessage` dice que cubre las formas usuales | Sonda: `redactErrorMessage('access_token: <valor>')` devuelve el texto sin cambios | Extender `SENSITIVE_PAIR_PATTERN` a `[=:]\s*` para las mismas claves, con una prueba e idempotencia. Otra opción: ajustar el comentario y dejar el caso registrado para M16.1, donde se arman los mensajes |
